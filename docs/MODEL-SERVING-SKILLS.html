One Model, Three Ways to Serve It

Most blueprints call NVIDIA’s hosted API — these skills add on-cluster model serving

FROM CONVERSION

NIM Operator

  • Requires NIM Operator installed cluster-wide
  • Operator manages lifecycle & updates
  • Tied to NVIDIA NGC licensing
  • Simplest path — but least flexible
Created by /bp-convert-to-rhoai
NIM SERVING SKILL

NIM via KServe

  • RHOAI-native — no operator dependency
  • Same NIM models, different deployment
  • Replicates what the RHOAI Dashboard does
  • ServingRuntime + InferenceService + PVC
Created by /bp-add-nim-serving
vLLM SKILL

vLLM

  • Models from HuggingFace
  • RHOAI ships a supported vLLM image
  • Not all architectures supported
  • Compatibility checked per-model, not assumed
Created by /bp-add-vllm-support

Additive approach: each skill adds its own Helm templates. At deploy time, enable the path you want with a single --set flag.

/bp-add-nim-serving

NIM Serving Skill: Replicating the Dashboard in Helm

🔍 Phase 1: NIM Discovery SUB-AGENT

Scans the blueprint for every NVIDIA model reference. Classifies each model by type (LLM, Embedding, Reranking, VLM) and detects existing NGC secrets.

→
👤 Phase 2: User Decisions USER

Presents each discovered model with its resource requirements (GPU count, CPU, memory, PVC size) and asks the user to confirm or adjust. Storage class and GPU tolerations are auto-resolved from the blueprint.

→
⚙️ Phase 3: Generate Resources SUB-AGENT

Creates three Helm templates per model: ServingRuntime (9 volume mounts), InferenceService (RawDeployment, GPUs), PVC (model cache)

↓
📝 Phase 6: Document MAIN

Updates the blueprint’s deployment docs with a NIM Serving section and prints a summary of all generated resources.

←
✅ Phase 5: Validate ×3 SUB-AGENT

Runs up to 3 iterations. Checks Helm lint, template rendering (enabled + disabled modes), all 9 volume mounts present, secret references, and endpoint rewiring correctness.

←
🔗 Phase 4: Endpoint Rewiring SUB-AGENT

Adds the InferenceService model endpoint to the blueprint so the app knows where to reach the locally served model.

The skill generates the same three KServe resources the RHOAI Dashboard creates when you deploy a NIM model through the UI — but through a single skill command, as version-controlled Helm templates.

Phase 2: Compatibility Check

1 Fetch config.json

Every HuggingFace model has a config.json with the model’s architecture class name.

→ "architectures": ["LlamaForCausalLM"]

2 Fetch registry.py

vLLM’s source file that maps architecture names to implementations. If the model’s architecture is listed here, vLLM can serve it.

→
3 Compare & Decide

Search registry.py for the architecture class as a dict key, e.g. LlamaForCausalLM inside _TEXT_GENERATION_MODELS.

Skill tool → Skill tool

Lessons Learned: Skill-to-Skill Invocation

Three approaches to chain /bp-add-vllm-support → /bp-add-nim-serving

📋 What we tried

vLLM flags an incompatible model → asks the user → invokes /bp-add-nim-serving live via the Skill tool, passing a handoff note — all inside the same session.

💥 One shared context, two full workflows

Running a skill inside a session that already ran a previous skill means the context keeps growing and gets less focused — which can degrade output quality, producing a silently wrong template caught only at deploy time, if ever.

→ Print the command; run it in a fresh session instead.

🔀 context: fork — a clean isolated context

A subagent that runs in its own fresh context — it does not inherit the parent conversation. The NIM skill would get a clean workspace, free of the vLLM session’s accumulated context. Solves the shared-context problem — but a fork is still a subagent, so AskUserQuestion is still stripped.

→ No config combination avoids both constraints at once.

🛑 Subagents can’t ask questions

AskUserQuestion is stripped from every subagent, unconditionally — forked, background, or not. No tool config restores it. Both skills’ entire “User Decisions” phase depends on it.

→ Approval gates must stay on the main thread, never delegated.
